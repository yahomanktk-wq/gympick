TASK: When an admin links a manager to a gym via the "헬스장 관리" screen's
매니저 연결 feature, the linked user's `profiles.role` must also become
'manager' (so ProfileScreen.tsx's role-gated "헬스장 관리" section, which checks
`user.role === 'manager'` at line ~953, actually appears for them). Currently
only `gyms.manager_id` is updated — `profiles.role` is never touched, so linked
managers see nothing different on their Profile screen.

CONFIRMED ROOT CAUSE: ProfileScreen.tsx gates the manager dashboard section
purely on `user.role === 'manager'`. `setGymManager()` in
src/lib/db/adminGyms.ts only writes `gyms.manager_id` and has no side effect on
`profiles.role`.

FILE: src/lib/db/adminGyms.ts (setGymManager), possibly src/screens/admin/AdminDashboard.tsx
if the role-sync logic is better placed at the call site.

============================================================
Before writing new logic, find how the EXISTING "매니저 신청 승인" flow (in
AdminDashboard.tsx's manager-applications queue, or wherever

inventing a new convention. Report what you find before proceeding.

============================================================
STEP 1 — Update setGymManager to sync profiles.role
============================================================
Modify `setGymManager(gymId: string, managerId: string | null)` so that:

1. WHEN LINKING (managerId is a non-null string):
   - After successfully updating `gyms.manager_id`, check the linked user's
     current `profiles.role`.
   - If it's currently `'user'`, update it to `'manager'` (mirroring STEP 0's
     found convention).
   - If it's already `'manager'`, no change needed (no-op, don't error).
   - If it's `'admin'`, DO NOT downgrade/overwrite it to `'manager'` — leave
     admin accounts as admin. Log a dev warning if this case is hit
     (`if (__DEV__) console.warn(...)`) so it's visible during testing, but
     don't change the role.

2. WHEN UNLINKING (managerId is null):
   - Before clearing `gyms.manager_id`, capture which user WAS the manager for
     this gym (fetch the gym's current `manager_id` first, or accept it as an
     additional parameter from the caller if the caller already has it —
     whichever is simpler given the existing call sites).
   - After successfully clearing `gyms.manager_id`, check whether that same
     user still manages ANY OTHER gym:
     `select id from gyms where manager_id = '<that user id>'`
     (this query naturally excludes the just-unlinked gym since its
     manager_id was already cleared).
   - If zero other gyms remain AND their current `profiles.role` is
     `'manager'` (not `'admin'` — never touch admin accounts), revert their
     `profiles.role` back to `'user'`.
   - If they still manage at least one other gym, leave their role as
     `'manager'` — do not downgrade.

3. Wrap the role-sync logic so a failure in it doesn't silently corrupt the
   primary `gyms.manager_id` write — the gym-manager link/unlink itself should
   already have succeeded before role-sync runs; if role-sync fails, throw/log
   clearly but the caller should still know the primary action succeeded (e.g.
   don't roll back the gym update — but do surface the role-sync failure
   somehow, at minimum a `console.warn` with enough detail to debug later, since
   this project doesn't have a broader error-reporting system to hook into for
   this task's scope).
