GOAL

Add a new admin-only screen showing user statistics, reachable from a new queue
card on the AdminDashboard home view (same pattern as existing cards like
'머신 카탈로그' or '브랜드 저작권' — i.e. an info/analytics card, not a
pending-review-count card).

Required metrics on the new screen:
1. 전체 가입자 수 (total registered user count)
2. 역할별 분포 (role breakdown: 일반 유저 / 매니저 / 어드민 counts, e.g. from
   profiles.role)
3. 최근 N일 신규가입 추이 (recent signup trend — last 7 or 14 days, grouped by day)
4. 활성 유저 (active users — based on most recent login/activity timestamp
   available in the schema)

STEP 1 — Investigate before building anything

1. Inspect the Supabase `profiles` table schema (and `auth.users` if accessible
   from the client with current RLS/permissions — likely it is NOT directly
   queryable from the client, so plan around using `profiles` only). Identify:
   - The exact column for role (e.g. `role`), and its possible values.
   - Whether there's a `created_at` (or similar) timestamp column usable for
     signup trend.
   - Whether there's any column that reflects "last active" or "last login"
     (e.g. `last_sign_in_at`, `updated_at`, or similar). If nothing reflects
     actual login recency, note that clearly — do not fabricate a proxy metric
     without flagging it as an approximation (e.g. using `updated_at` on the
     profile row is NOT the same as last login and should be labeled as such
     in the UI if used, or the "활성 유저" metric should be omitted/marked as
     unavailable if there's truly no usable signal).
2. Check whether the client (anon/authenticated role, whatever the admin user's
   Supabase session uses) actually has RLS permission to read all rows of
   `profiles`, not just their own. If not, this feature cannot work client-side
   as-is — report this back and stop before implementing, rather than writing a
   query that will silently return incomplete/empty results for other admins.
3. Check package.json for any already-installed charting library (e.g.
   react-native-svg based chart libs, victory-native, etc.). Do NOT install any
   new dependency for this. If nothing suitable exists, plan to render the
   signup trend as a simple custom bar visualization using plain Views (bar
   height proportional to count) rather than adding a chart library.

Report findings from Step 1 before proceeding to Step 2. If RLS blocks reading
all profiles, STOP here and report — do not implement a broken/partial feature.
