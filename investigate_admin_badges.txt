■ 배경/증상
어드민 대시보드의 각 항목 알림 배지 숫자가 실제와 다르게 표시된다.
- 예: 매니저 신청이 실제로는 0건인데 배지에 "3"으로 표시.
- 두 위치 모두 오류:
  (1) 프로필 화면(ProfileScreen)의 '관리자 패널'(AdminSection) 미리보기 배지
  (2) 탭으로 진입하는 어드민 대시보드 화면(AdminDashboard)의 배지/통계
- 여러 배지(헬스장 심사/수정/신고/매니저 신청 등)가 전부 틀림.

■ 확인된 사실 (참고 — 재확인만)
- ProfileScreen L27: import { PENDING_GYMS, PENDING_EDITS, FLAGGED_ITEMS } from '../data/mockAdmin'
  → AdminSection(대략 L253)이 이 mock을 직접 세서 배지에 표시 (프로필 배지 오류 원인 확정)
- AdminDashboard는 mockAdmin을 import하지 않음. count는 Supabase fetch 결과(state)를 셈.
  그런데도 탭 화면 배지가 틀리다면 → fetch 함수가 실패 시 mock을 반환(fallback)하는지 확인 필요.

■ 목표
"탭 화면(AdminDashboard) 배지가 왜 틀리는가"를 확정하는 것이 핵심.
그리고 프로필/탭 양쪽의 데이터 소스(실제 Supabase vs mock)를 명확히 정리.

■ 결과 출력
  D:\시작\gympick\ADMIN_BADGE_INVESTIGATION.txt 한 파일에 섹션별 정리.

  - 각 섹션 끝 "[분석]"
  - 불확실하면 "확인 필요" 표기

[조사 2] fetch 함수들의 mock fallback 여부 (탭 오류의 핵심 용의자)
================================================================================
아래 파일들에서 각 fetch 함수가 '실패 시 무엇을 반환'하는지 그대로 덤프:
- src/lib/db/managerRequests.ts → fetchManagerRequests
- src/lib/db/gymInfoReports.ts (또는 gymReports 관련) → fetchGymInfoReports
- src/lib/db/gymRegistrationRequests.ts → fetchGymRegistrationRequests
- src/lib/db/machineRequests.ts → fetchMachineRequests
- (pendingGyms/pendingEdits/flags를 로드하는 함수가 있으면 그것도)

각 함수에서:
- Supabase 조회 실패(error) 또는 빈 데이터일 때 return 하는 값
- mock 데이터(예: MOCK_*, PENDING_*, 하드코딩 배열)를 반환하는지
- 정상일 때 반환 형태 (status 필드 포함 여부)

[분석]
- 어떤 fetch가 실패 시 mock을 반환하는지 (그러면 탭 배지가 mock 개수로 뜸)
- status 필드가 'pending'으로 채워지는 mock이 있는지 (배지 카운트에 잡힘)
- 탭 화면 배지 오류의 직접 원인 지목
