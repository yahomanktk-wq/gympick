이 파일을 읽고 확인이나 중단 없이 끝까지 완료해줘.

## 배경
Supabase에서 "Fair Use Policy" 경고 메일을 받았음. 캐시된 egress 대역폭이
5.5GB 기준을 초과할 것으로 예상됨 (2026-08-22부터 적용).
목적은 원인을 파악하는 것. 이 태스크에서는 절대 코드를 수정하지 말고
조사 결과만 보고할 것.

## 조사 범위

### 1. 이미지 요청 패턴 조사
- `Image.getSize()` 호출이 남아있는 위치를 전체 검색 (grep -rn "Image.getSize")
  - HomeScreen.tsx의 OunwanCard에서 이미 getSize를 쓰고 있는데,
    이게 매번 마운트될 때마다 원본 이미지를 네트워크로 다시 요청하는지 확인
  - getSize가 실제로 이미지를 다운로드하는지, 아니면 헤더만 읽는지 확인 필요
  - expo-image로 마이그레이션되지 않은 화면/컴포넌트가 남아있는지 전체 검색
    (react-native의 기본 `Image` 컴포넌트를 그대로 쓰는 곳 전부 나열:
    `import { Image } from 'react-native'` 후 실제 사용처)

### 2. feedPostsCache.ts 캐시 동작 확인
- TTL이 몇 분/초로 설정되어 있는지
- 캐시가 실제로 재사용되는지, 아니면 화면 진입마다 새로 fetch하는지
  (HomeScreen의 useFocusEffect가 탭 전환마다 fetchActiveFeedPosts를 다시 호출하는데,
  이게 캐시를 타는지 아니면 매번 Supabase에 새로 요청하는지 확인)
- 여러 화면(HomeScreen, WorkoutFeed 등)에서 동일한 피드 데이터를 각자 fetch하고
  있는지, 중복 요청 여부 확인

### 3. Supabase Storage 버킷 설정 확인
- `machine-images` 버킷과 기타 이미지 버킷(프로필 사진, 오운완 인증샷 등)의
  Cache-Control 헤더 설정 여부 확인 (코드에서 upload 시 cacheControl 옵션을
  주고 있는지 grep으로 확인: `.upload(` 호출부 전부 찾아서 옵션 나열)
- Storage에서 public URL을 만들 때 CDN 캐싱이 걸리는 형태로 요청하고 있는지
  (getPublicUrl 사용 패턴 확인)

### 4. 이미지 크기/용량 조사
- 실제 업로드되는 이미지 리사이징 로직이 있는지 확인
  (오운완 인증샷, 프로필 사진, 머신 이미지 각각)
- 머신 이미지가 800×800 WebP로 고정되어 있다고 알고 있는데, 그리드 뷰
  (2열, 작은 카드)에서도 원본 800×800을 그대로 받아오는지, 아니면
  썸네일 별도 버전이 있는지 확인

### 5. 반복 호출 가능성이 있는 지점 나열
- HomeScreen, JournalScreen, AdminDashboard, ManagerDashboard 등 주요 화면에서
  useEffect/useFocusEffect 안에 이미지 관련 fetch가 있는 곳을 전부 나열
  (탭 전환할 때마다 재실행되는지 여부 포함)
- FlatList/ScrollView에서 이미지 프리로딩이나 반복 렌더링으로 인해
  같은 이미지가 여러 번 요청될 가능성이 있는 컴포넌트 나열
  (MachineCatalogView의 그리드, RegisterGymAdminView의 머신 그리드 등)

## 출력 형식
아래 항목별로 정리해서 보고해줘 (코드 수정 없이 순수 조사 결과만):

1. Image.getSize / 미마이그레이션 Image 사용처 목록 (파일명, 라인, 코드 스니펫)
2. feedPostsCache.ts의 실제 TTL 값과 캐시 히트/미스 발생 조건
3. Storage upload 시 cacheControl 옵션 설정 여부 (버킷별로)
4. 이미지 리사이징/썸네일 로직 존재 여부
5. 대역폭을 많이 소모할 것으로 의심되는 지점 우선순위 Top 5
   (각 항목마다 왜 의심되는지 1-2줄 근거 포함)

이 조사 결과를 텍스트로 정리해서 보여줘. 코드는 절대 변경하지 마.
