## A. AdminDashboard.tsx

### A1. handleRejectGym does not handle manager/user gym registration proposals
- handleApproveGym searches across pendingGyms + gymRequests (manager proposals from
  gym_registration_requests table) and calls updateGymRequestStatus(id, 'reviewed')
  for those.
- handleRejectGym only calls updateGymStatus(id, 'rejected') and updates gymList
  (RegistrationGym state). It never touches gymRequests state or calls
  updateGymRequestStatus.
- Question: when a user rejects an item that originated from managerGymRequests
  (i.e., its id belongs to a gym_registration_requests row, not a RegistrationGym row),
  what actually happens? Does updateGymStatus silently no-op on an unmatched id? Does
  the UI still show it as pending afterward? Trace this end to end.

### A2. Manager proposal status mapping collapses non-pending states to "approved"
- In the managerGymRequests mapping:
  status: (r.status === 'pending' ? 'pending' : 'approved') as ReviewStatus
- gym_registration_requests rows can have status 'pending' | 'reviewed' | 'resolved'
  (per project conventions — 'rejected' is not a valid value in this table).
- Confirm whether a request with status 'reviewed' or 'resolved' (which could mean
  "processed" in either a positive or negative outcome) always displays as
  "✓ 승인됨" (approved) in GymDetailView, regardless of actual outcome. Confirm there
  is no separate signal (e.g. a rejection reason field) that would distinguish these.

### A3. Home dashboard stat cards are hardcoded
- In HomeView, the stats array hardcodes:
  '전체 헬스장': '8', '오늘 승인': '2', '전체 머신': '23'
- Note MACHINES.length is already used elsewhere in the same component for the
  machine catalog quick-menu item. Confirm these three stat values are indeed
  static literals with no data binding, and identify whether any nearby
  state/prop (registeredGymCount, MACHINES.length, gymReportCount, etc.) was
  clearly intended to replace them but wasn't wired in.

### A4. "최근 활동" (recent activity) list is hardcoded mock data
- Confirm the activity list in HomeView's "최근 활동" section is static array data
  with no connection to actual approval/rejection actions (reviewGym, handleApproveGym,
  handleRejectGym, reviewEdit, resolveFlag, etc.). Confirm there is no activity log
  table/store anywhere in the codebase that this could/should read from.

### A5. Machine catalog "approve" only updates local component state
- approveSelected (catApproved/catSelected state) has no call to any store or
  Supabase table. Confirm whether catApproved is persisted anywhere (check for
  a matching store file, e.g. something like approvedMachineStore or a Supabase

### A6. RegisterGymAdminView (직접 등록) data source vs. user-facing gym data

## B. HomeScreen.tsx

### B1. computeStreak recency guard appears missing
- Per prior project notes, a "streak recency guard" was supposedly added: if the
  most recent workout log is not from today or yesterday, computeStreak should
  return 0.
- The current computeStreak function in this file has no such check — it just
  sorts unique dates descending and counts consecutive days from the most recent
  entry, regardless of how long ago that was.
- Confirm this by reading the function as it exists in the actual project file
  (not just this snippet) and check git history/blame if possible for whether
  this guard was added and then reverted, or never actually applied to this
  function despite being noted as done.

### B2. Potential timezone mismatch in date comparisons
- computeStreak uses l.date.slice(0, 10) (string slice) for grouping, but the
  streak-break comparison uses new Date(uniqueDates[i-1]) then
  .toISOString().slice(0,10) (UTC-based).
- Investigate what format WorkoutLog.date is actually stored in (local KST
  ISO string vs UTC ISO string) at the point of insertion (check the workout
  logging / save flow, e.g. wherever workout_sessions rows are created).

  the wrong calendar day due to this UTC conversion, which would affect both
  the streak count and the "이번 주 운동" weekly thumbnail matching (isSameDay).

### B4. CTA card label vs. actual navigation target

  not to 'FindGym'.
- Investigate the LogWorkoutScreen flow: does it include a gym-selection step
