PART B — Code investigation (do this yourself, thoroughly)

1. Identify every screen/component in the app that renders a list or grid of
   images (this is likely the primary source of perceived stutter — many images
   loading/rendering close together). At minimum check:
   - MachineCatalogView / RegisterGymAdminView's machine grid (AdminDashboard.tsx)
   - FindGymScreen's gym/machine search results
   - GymDetailModal's machine tab grid
   - WorkoutFeed / 오운완 feed screens
   - HomeScreen's weekly thumbnail row and AutoScrollOunwan
   - JournalScreen's session thumbnails
   - Any other screen rendering more than ~6 images in a scrollable list/grid

   For each one found, report:
   a. Whether it uses FlatList (with virtualization props like
      initialNumToRender/maxToRenderPerBatch/windowSize/removeClippedSubviews —
      check which are actually set, per the pattern already correctly used in
      AdminDashboard.tsx's RegisterGymAdminView) or a plain ScrollView.map()
      (which renders everything at once regardless of what's visible on screen
      — a common source of jank for image-heavy lists).
   b. Whether it uses expo-image (with caching) or plain React Native `Image`
      (per project history, expo-image migration was done for some screens —
      confirm exactly which screens still use plain Image and haven't been
      migrated).
   c. The actual image dimensions being requested (the URL/source) versus the
      display size the image is rendered at (e.g. is an 800×800 machine image
      being displayed in a 60×60 thumbnail slot with no resizing, which wastes
      bandwidth and decode time)?

2. Check the machine image pipeline specifically (per project conventions:
   Supabase Storage `machine-images` bucket, 800×800 WebP, filename = machine
   id) — are these images ever requested at a smaller size for grid/thumbnail
   contexts, or is the full 800×800 file always downloaded and decoded
   regardless of how small it's displayed on screen? Confirm by checking how the
   image URL is constructed wherever machine images are rendered.

3. Check whether any screen re-fetches or re-renders the same images repeatedly
   in a way that would defeat caching (e.g. a URL that includes a changing query
   param/timestamp/signed-token that changes on every fetch, which would make
   expo-image's cache treat it as a different image each time even though the
   underlying content is identical — check especially the manager-verification-
   docs signed URLs from a recent task, and any other place using signed URLs
   with short expiry, to see if they're used somewhere they'd be re-requested
   often).

4. Check current list-rendering performance settings for consistency — if some
   grids already have good FlatList windowing config (per AdminDashboard.tsx's
   existing pattern) and others don't, that inconsistency itself is useful
   diagnostic information.
