TASK: Build a new "관리자에게 문의하기" (contact admin) feature end-to-end.
User side: submit a free-form inquiry (title + content) from Profile screen, and
view their own inquiry history with status (pending/answered) and the admin's
answer once given. Admin side: a new queue in AdminDashboard.tsx to view pending
inquiries and submit an answer.

PRECONDITION: A new Supabase table `user_inquiries` must already exist (the user
was given the SQL to run separately in Supabase SQL Editor before this task starts).
Do NOT attempt to create or alter tables via this task — only write application
code against the existing table. If any Supabase call in this task fails because
the table doesn't exist yet, stop and report that the SQL step hasn't been run yet,
rather than working around it.

Table shape (for reference — do not create it, it should already exist, and HAS
already been created and confirmed by the user via Supabase SQL Editor):
    user_inquiries (
      id           text primary key,          -- client-generated, TEXT
      user_id      uuid not null,              -- references profiles(id), NOT text
      title        text not null,
      content      text not null,
      status       text not null default 'pending',  -- 'pending' | 'answered'
      answer       text,
      answered_at  timestamptz,
      created_at   timestamptz not null default now()
    )

IMPORTANT: unlike this project's other custom entities (gyms, machines, etc.) which
use client-generated TEXT ids, `user_id` here is a Supabase Auth UUID (matches
`profiles.id`, which is also uuid) — this is the one exception to the "everything
is TEXT" convention, because it must match Supabase Auth's native id type. Do not
try to "fix" this to TEXT. Only the inquiry's own `id` column is a client-generated
TEXT id, following the existing convention.

Admin role check in this codebase is done via `profiles.role === 'admin'`
(confirmed in context/AuthContext.tsx: `mapSupabaseUser` reads `role` from the
`profiles` table, and `useAuth().user.role` is what AdminDashboard.tsx / other
admin-gated code already checks). There is no separate `users` table — everything
keys off `profiles`, whose `id` equals the Supabase Auth uuid. `user.id` from
`useAuth()` is already that same uuid as a string — pass it directly as `user_id`
when calling `submitUserInquiry`, no conversion needed.
